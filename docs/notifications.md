# 管理员 Telegram 通知

状态：首批功能及隔离全量、浏览器、容器验收已完成，待精确 Git 提交镜像和 CI 检查。
尚未发布到 `main`，也未升级生产实例。
整体验收结果以[测试记录](testing.md)和[交接记录](refactor-handoff.md)为准。

## 支持什么

管理后台的“通知设置”页用于配置一个管理员 Telegram Bot 和一个数字 Chat ID，
预览套餐临期消息、主动发送测试、查看投递记录，以及在核实风险后人工重试。
套餐提醒默认关闭；默认提前 7 天，范围为 1–365 天，默认时区为
`Asia/Shanghai`，每日扫描起点固定为该时区的 09:00。

业务入口参考[官方系统设置](https://miaomiaowux.com/docs/en/system-settings/)及固定
`miaomiaowuX` 源码中的
[notify_config.go](https://github.com/tajiaoyezi/miaomiaowuX/blob/c12ce653bc07fe30426b7dfcb85076974b7be0e0/internal/handler/notify_config.go)、
[notify_scheduler.go](https://github.com/tajiaoyezi/miaomiaowuX/blob/c12ce653bc07fe30426b7dfcb85076974b7be0e0/internal/handler/notify_scheduler.go)。
这里没有移植完整的 [mmwX-tgbot](https://miaomiaowux.com/docs/en/tool-mmwx-tgbot/)：
用户 Telegram 绑定、Bot 命令、Mini App、20 点日报、登录/流量/服务器阈值提醒、
公告和人工续费审批均未接入。通知不会扣款、延长套餐、重置流量或下发 Agent 命令，
也没有激活码或许可证门槛。

## 配置与测试

1. 用管理员账户登录“通知设置”。普通订阅用户不能读取或修改这些配置。
2. 填入有权使用的数字 Chat ID，选择“替换 Bot Token”并输入 Token。
   不接受聊天用户名、邀请链接或自定义 API 地址。
3. 初次配置时先保持套餐提醒关闭，保存后检查上方“已保存配置”。
   新 Token 在保存请求开始时即从输入框清空，失败也不会自动填回。
   GET 只返回“是否已配置”，不返回 Token 或尾号。
4. 点击“预览已保存配置”。没有候选时显示明确标注的示例；有候选时最多展示
   20 个用户及一条消息正文。预览使用已保存配置，不使用未保存的草稿。
5. 如需真实测试，点击“发送测试消息”，核对并确认目标 Chat ID 后提交。
   这会向目标发送一条固定测试消息；提醒开关关闭不影响管理员主动测试。
6. 确认目标和投递记录后，再按需要开启套餐提醒。

读取、保存和预览请求本身不发送消息。但开启提醒后，独立后台任务会在所选时区
09:00 之后每分钟扫描，符合条件的提醒可能很快发出。不要在真实环境开启开关，
再把“保存不发送”理解成没有后台通知。

提醒会把**用户名、套餐名称和到期时间**发到选定聊天。请先确认聊天成员和机器人权限；
正文是有限长度的纯文本，不附带订阅链接、用户凭据或证书，不启用链接预览及付费广播。
生产测试需要操作者自己的授权 Token 和测试聊天；仓库里的隔离替身测试不能证明
真实 Telegram 已接受消息。

## 谁会收到提醒

消息统一发往管理员设置的 Chat ID，不是逐个发给订阅用户。候选用户必须处于启用
状态、未进入删除流程、仍绑定有效套餐，并且到期时间在当前时刻之后、未来 N 个
本地日历日之内。流量已经用完的用户仍可符合临期条件。

每个用户实例、套餐和精确到期时刻形成一个持久事件。修改显示名称、切换开关、
更换 Token、修改时区或重启服务，不会重新发送已有接受回执的同一事件。
套餐延长后产生的是新的到期事件；已经过期的套餐不会补发“即将到期”。

重启后只检查当前仍符合条件的事件，不逐日补发停机期间的历史消息。预览人数包括
已有投递记录的候选，**不是下一轮待发送数量**；后台还会检查去重记录、开关、
当前套餐、等待时间和密钥状态。

## 投递状态与人工重试

| 页面状态 | 含义 |
| --- | --- |
| 排队中 | 请求已持久保存，还未开始当前发送尝试。 |
| 发送中 | 已记录发送尝试；可能已经开始联网。 |
| Telegram 已接受 | 收到有效 `ok=true` 和匹配的 Message 回执，不代表收件人已读。 |
| 失败 | 已知的拒绝或发送前失败；查看固定错误说明。 |
| 结果未知 | 消息可能已发出，但无法确认结果；不会自动重新发送。 |
| 已取消 | 未发送任务已不适用或配置被清空；不能撤回先前已发出的消息。 |

状态判断按 [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage) 的有效回执，
不把 HTTP 200 直接当成成功。断线、读取超时、模糊的服务端异常，或者发送后未能
保存回执，都可能成为“结果未知”。Telegram 没有供这里使用的客户端发送幂等键，
本地队列不能保证对方绝对只收到一次。

同一测试或重试请求使用同一个 UUID；重复提交相同请求不会另建投递。
页面每 5 秒进行只读查询。若提交响应丢失，先“查询原请求”；查不到记录也不证明
先前请求未提交。页面提供“使用同一请求 ID 再次提交”，需再次确认，且不会偷偷
换成新 UUID。离开页面不会取消服务器上的任务，回到页面后应先检查投递记录。

“结果未知”只有在旧尝试的等待期限结束、状态仍允许时才能人工重试，还须确认
可能重复的风险。重试使用此时已保存的配置；确认窗口同时显示当前目标和旧目标。
旧尝试、原目标和晚到回执会保留，不覆盖新尝试的结果。

自动重试仅用于明确的发送前连接失败、任务领取后尚未联网便发现剩余期限不足，
或有效的限流回应。单条投递在自动流程中最多累计 3 次尝试，包含首次尝试，
不是在首次之外再重试 3 次，并且必须遵守等待时间。其他拒绝需检查配置；
人工重试不会绕过已接受事件的去重限制。同一 Chat ID 有持久的发送间隔和在途限制。

关闭套餐提醒会取消未发送的套餐提醒，但保留主动测试。清空 Chat ID 或清除 Token
会取消全部未发送任务；已发送或结果未知的历史保留原目标。任何设置修改都无法
撤回已经发出的消息。

## 密钥、备份与恢复

配置和投递记录存放在现有 SQLite 数据库的五张独立 `notification_*` 表中。
Bot Token 用单独的通知密钥加密，不能用 TOTP、证书或外部订阅密钥代替。

文件型 SQLite 默认使用数据库旁的 `notifications` 目录。标准 Docker 镜像中为：

- 数据库：`/var/lib/open-node/open-node.db`。
- 通知目录：`/var/lib/open-node/notifications`，权限 0700。
- 密钥：`telegram.key`，权限 0600。
- 初始化标记：`telegram.initialized`，权限 0600。

目录和文件须归运行服务的用户所有；标准镜像为 UID/GID 10001。
首次保存 Token 才创建密钥和标记；只打开页面不会创建。密钥缺失、替换错误、
标记不匹配、符号链接、硬链接或宽松权限会阻止发送，不会自动生成新密钥覆盖原数据。

恢复时应同时恢复**同一备份中的 SQLite 数据库和完整 notifications 目录**，
包括原密钥与初始化标记。按[部署文档](deployment.md)中的停服整卷备份流程操作，
不要只复制运行中的主数据库文件，遗漏 WAL 或秘密文件。
标准 Docker 数据卷已覆盖这些默认路径。更换主机时还要恢复所有权和私有权限。

密钥故障时仍可保留 Token 密文并关闭提醒；替换/清除 Token、测试和人工重试须先
恢复原密钥。关闭开关不能修复错误备份。不要删除数据库中的指纹，或手工换新密钥
来消除错误提示。

自定义部署可以设置 `OPEN_NODE_NOTIFICATIONS_STATE_DIR`，但必须使用绝对、
非根、无路径穿越的独立目录，不能与证书或外部订阅密钥目录重叠。
若放到标准数据卷之外，备份方案也必须覆盖它；标准 Compose 不自动透传该覆盖项。
内存/URI SQLite 不会推导密钥路径，须显式提供。
此首批实现只支持 SQLite 通知存储，不声称具备 PostgreSQL 通知运行能力。

发送固定连接 `api.telegram.org:443` 并校验证书与主机名，不使用环境代理、不跟随
重定向、不允许跳过 TLS。连接上限 5 秒，完整发送尝试上限 20 秒，回包有严格大小
和协议限制。数据库写事务不会跨越网络等待，重启恢复也不会直接重放发送中任务。

## API 与验收

全部接口位于 `/api/v1/notifications`，要求管理员会话；写请求还要求现有
Origin/CSRF 校验。响应禁止缓存，不回显提交的 Token、原始错误正文或供应商描述。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /settings`、`PUT /settings` | 读取或按配置版本保存；Token 操作为 keep/replace/clear。 |
| `POST /preview` | 读取已保存版本的候选和正文，不排队。 |
| `POST /test` | 以请求 UUID 创建持久测试投递，返回 202。 |
| `GET /deliveries`、`GET /deliveries/{id}` | 查询最近投递和各次尝试。 |
| `GET /requests/{request_id}` | 核实原始测试或重试请求对应的投递。 |
| `POST /deliveries/{id}/retry` | 按配置版本、旧尝试 ID 和重复风险确认进行人工重试。 |

实现与官方差异见[设计记录](notifications-plan.md)；当前通过与未通过的检查、
源代码哈希、故障注入和隔离环境路径统一记入[测试记录](testing.md)。
